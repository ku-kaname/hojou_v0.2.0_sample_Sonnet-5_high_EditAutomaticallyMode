## 進捗ログ

### 2026-10-11
**◆対応者：Claude Sonnet 5**

- **指摘1（高）：テストハーネス（`postgres_container_stopped`フィクスチャ）が、本環境（Windows + Docker Desktop）でホスト側ポートフォワーディングを恒久的に破損させる事象を発見**
    - DB接続不可状態を再現するため、`conftest.py`の`postgres_container_stopped`フィクスチャは、結合テスト全体で共有している使い捨てPostgreSQLコンテナ自体を`docker stop`/`docker start`していた。`test_health_check.py`のNo.2実行後、`docker start`→コンテナ内部の`pg_isready`は成功するが、ホスト側（127.0.0.1:割当ポート）へのTCP接続が約5分間一度も確立できない事象を手動の診断スクリプトで確認した。これは待てば直るタイミングの問題ではなく、本環境固有の恒久的なポートフォワーディング破損であり、以降の全テストがDB接続タイムアウトで失敗し続けた（1回目の実行：2 passed, 13 errors、2回目：2 passed, 14 errors）。
    - `docker pause`/`docker unpause`方式も検討したが、ポートフォワーディングは保持されるものの、pause中もTCP接続自体（SYN/ACK）はカーネルレベルで即座に成功してしまい、アプリ側に`connect_timeout`の設定がないため実クエリが無期限にハングするリスクがあり、採用を見送った。
    - 対応：共有コンテナ自体は一切操作しない方式に変更した。ヘルスチェック処理が参照するengine（`app.main.engine`）を、`monkeypatch`で「何も待ち受けていない未使用ポート」を指す一時engineに差し替える`db_connection_unreachable`フィクスチャに置き換えた。一時engineには`connect_args={"connect_timeout": 3}`を明示的に設定した（本環境では、未使用ポートへの接続はタイムアウト未設定の場合10秒以上ハングすることを確認したため）。
    - `レビュー指摘表/結合テスト工程/共通/結合テスト共通設定_レビュー指摘表.md`を新規作成し、識別項目を機能名＝「結合テスト共通設定」・HTTPメソッド／エンドポイント＝「-」（特定のエンドポイントに属さない共通処理のため）として記録した。
    - `conftest.py`の`postgres_container_stopped`を`db_connection_unreachable`に置き換え、`test_health_check.py`のテスト関数引数も追随して修正した。
    - 仕様書側にも、再現方式が「コンテナ一時停止」であるかのような前提条件の誤記があったため、`ヘルスチェック_結合テスト仕様書_v0.2.0_レビュー指摘表.md`を新規作成し、`ヘルスチェック_結合テスト仕様書.md`をv0.2.0からv0.3.0に更新（No.2の前提条件を「DB接続先が一時的に応答のない接続先に差し替えられている」に修正）した。
    - 修正後、`pytest app/tests/integration`は30分超かかっていた実行が5.55秒に短縮され、ヘルスチェック2件・ログアウト6件・ログイン4件（計12件）が合格することを確認した（この時点ではログインの残り3件が後述の指摘2により失敗）。
- **指摘2（高）：`database.get_db`の例外種別を問わないロールバック方針により、ログイン失敗回数・ロック機能が実運用でも一度も機能していなかった本番コードの欠陥を発見**
    - ハーネス修正後の実行で`test_login_endpoint_003`・`004`・`005`が失敗。原因は、`services.login`が認証失敗時に`crud.update_user_login_result`（`db.flush()`のみ、コミットなし）を呼んだ直後に`credentials_exception`（HTTPException 401）を無条件で`raise`しているが、`database.get_db`は「呼び出し元で例外が発生した場合は常にロールバックする」設計のため、業務上正常な応答であるHTTPExceptionでも無条件にロールバックされ、`login_failure_count`・`locked_until`の更新が一度も永続化されないこと。単体テストはDBセッションをモックしていたため、この`get_db`実装との組み合わせによる不整合をこれまで検知できなかった。`services.py`内の他の全`raise HTTPException`箇所（約30件）を確認し、書き込み後に例外を送出しているのは`login`のみであることを確認した。
    - `レビュー指摘表/結合テスト工程/共通/ログイン_レビュー指摘表.md`の項番3として記録した。
    - 対応：`backend/app/database.py`の`get_db`を、HTTPException発生時はコミットし、その他の例外発生時のみロールバックするよう修正した（`from fastapi import HTTPException`を追加）。本変更は書き込み後に例外を送出する唯一の処理（`login`）にのみ挙動の変化をもたらし、他の処理（検証がDB更新より前に完結している）には影響しない。
    - 対応に関する設計書の有無を`設計書/`配下で確認したが、`get_db`のコミット／ロールバック挙動を明示的に文書化した設計書は存在しなかった（既存の設計書は依存性注入としての位置づけのみ記載）。本件はコードのdocコメント自体が挙動の記述を兼ねているため、docコメントの修正のみで対応した。
- **指摘3（高）：ナイーブ／aware datetimeの比較不整合による`TypeError`を発見**
    - 指摘2対応後、`test_login_endpoint_005`で`TypeError: can't compare offset-naive and offset-aware datetimes`が発生。原因は、`models.py`の`locked_until`カラムが`DateTime`（タイムゾーン情報なし）で定義されているため、DBから取得した`user.locked_until`はnaiveなdatetimeとなるが、比較対象の`now`（`dt.datetime.now(dt.UTC)`）はawareであり、`services.login`96行目で直接比較できないこと。単体テストは`user`をモック（`SimpleNamespace`）で代替し、`locked_until`にaware値を直接設定していたため、この型不整合を検知できなかった。`services.py`内の他の`now`使用箇所を全て確認し、DBから取得したdatetimeカラムの値と直接比較しているのは本箇所のみであることを確認した。
    - 同じ`ログイン_レビュー指摘表.md`の項番4として記録した。
    - 対応：`services.login`で、`user.locked_until`がnaiveな場合にUTCとして補完した上で`now`と比較するよう修正した（DBへの書き込み内容には影響しない）。
- 上記2件の本番コード修正後、`uv run pytest app/tests/integration -v`を再実行し、15ケース全て合格したことを確認した（実行結果：`test_specification/integration_test_specification/evidence/backend_結合テスト実行結果_2026-10-11.log`）。
- `uv run pytest app/tests/unit`を実行し、既存の単体テストへの影響がないことを確認した（`test_services_auth.py`等のログイン関連テストは全て合格）。7件の失敗（`test_services_loan_lending.py`・`test_services_loan_requests.py`）が見られたが、本修正前（`git stash`で確認）から存在する`crud.count_overlapping_loan_requests`のモック設定に起因する既存不良であり、本タスクの変更とは無関係であることを確認した。この既存不良は、該当機能（貸出申請・承認／貸出・返却・履歴）の単体テストバックログ側の課題として別途対応が必要（本タスクのスコープ外）。
- 全15ケース合格を確認後、3つの結合テスト仕様書（ヘルスチェック・ログイン・ログアウト）のテスト工程欄（エビデンス・担当者・実施日・実施結果・再鑑者・再鑑日）に実行結果を記載した（担当者・再鑑者ともにClaude Sonnet 5、実施結果はいずれも"OK"）。
